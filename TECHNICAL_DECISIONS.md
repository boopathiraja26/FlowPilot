# FlowPilot Technical Decisions

## Product scope

- FlowPilot is a general AI-powered workflow automation platform for visually designing, executing, and monitoring workflows.
- Employee onboarding is a representative demonstration workflow, not a dedicated employee intake product. The first implementation phase provides a generic manual JSON trigger → configurable AI/email steps → persisted execution logs. It does not add a dedicated employee intake system.
- Target navigation/capability areas are Dashboard, Workflows, Executions, Integrations, Schedules, and Settings (core), plus Analytics (advanced). Settings currently cover account name/email and password; notification preferences, broader account security controls, and inbound webhook triggers remain planned.
- Billing, quotas, support, privacy policies, tenant administration, and commercial SaaS operations are not prerequisites for the first portfolio release.

## Confirmed from the current repository

- **Application split:** Next.js 15 client and Express/TypeScript API remain separate workspaces.
- **Persistence:** PostgreSQL via Prisma. The schema contains users, workflows, ordered steps, workflow executions, and execution logs; migrations are checked in.
- **Authentication:** bcrypt password hashing and JWT access tokens stored in an HTTP-only cookie. Login, registration, logout, and authenticated workflow/execution routes exist.
- **Execution:** the compatibility endpoint validates configuration and executes steps synchronously. The dashboard path persists a queued execution and uses a separate worker to execute the same validated, sequential engine. Template references resolve against trigger input and completed prior steps; unresolved and forward references fail explicitly. Step context remains in memory. New logs persist status and generic messages only, never step outputs or provider error details. Older logs may still contain AI output.
- **Workflow lifecycle:** the existing `WorkflowStatus` enum supports `DRAFT`, `ACTIVE`, and `ARCHIVED`; no schema migration is required. The UI maps deactivate/restore to `DRAFT`, and restore from archive returns to draft. Duplication creates a new draft and copies steps in their existing order while blanking credential-like config keys, URL user-info, and sensitive URL query values.
- **Execution history:** query-param requests support bounded `page`/`limit` plus optional status/workflow filters, and return pagination metadata alongside the existing `data.executions` array. Requests without query parameters retain the historical unpaginated list behavior for compatibility. The dashboard uses an owner-scoped aggregate for all-time metrics and requests only its five newest executions; execution detail remains a per-execution record with its logs.
- **Delay:** the step editor stores milliseconds. Runtime validation allows whole numbers from zero through the Node.js timer maximum, matching the existing unit and avoiding an unrequested seconds conversion or arbitrary cap.
- **Retry boundary:** retry is not exposed yet. Email and webhook steps can create external side effects; without durable idempotency/recovery, retry could send duplicates.
- **Trigger input:** authenticated manual runs accept a generic JSON object. Durable one-time and interval schedules are implemented; inbound webhook triggers are not.
- **Dashboard data:** `/dashboard` calls the authenticated `/workflows`, `/analytics/dashboard-summary`, and bounded `/executions?page=1&limit=5` endpoints in parallel. Execution totals and terminal success rate are lifetime metrics computed by a user-scoped database aggregation; recent activity is limited to five rows. `/analytics` separately provides owner-scoped database aggregation for 7/30/90-day execution reporting.
- **Analytics:** `/analytics` uses a parameterized PostgreSQL aggregate query joined through `workflows.userId`, grouping persisted executions by UTC creation day and status. Success rate is completed / (completed + failed); queued and running are excluded. Average duration includes only completed rows with non-null, non-negative start/end timestamps. No workflow inputs, outputs, or integration credentials are queried or returned. The API accepts only 7, 30, or 90 days.
- **Account settings:** `GET/PATCH /auth/me` and `POST /auth/password` require authentication and use only the authenticated user ID for reads/writes. Profile responses select and serialize id, name, email, avatar, and timestamps, never the password hash. Password changes require the existing password, use the registration password strength rules, hash with bcrypt, and return no credential material other than the replacement bearer token for the active session. Email uniqueness conflicts return a generic conflict message.
- **Session invalidation:** A `passwordVersion` integer defaults to 0 and is included in new JWTs. Middleware compares the token version with the database value; legacy tokens without the claim are treated as version 0. Password changes atomically increment the version and issue a replacement token, invalidating other sessions on their next request. Profile updates do not change the version, so they do not unexpectedly log out users. The additive migration is checked in but has not been applied.
- **Workflow configuration:** AI/email/webhook templates resolve against trigger and prior-step context. A reference such as `{{step_1.employee_email}}` reads the earlier step's output; a reference to a later step or a missing value fails rather than becoming an empty string. Step config is validated before execution. The onboarding welcome-email layout is used only for an employee-onboarding trigger; other workflows use configured content or escaped AI output. Dynamic values are escaped before insertion into the onboarding HTML template.
- **Integrations:** Gemini uses the configured server model and reports missing credentials/empty responses; SMTP email and HTTP webhook handlers exist. Required credentials/configuration belong on the server, not in the client.
- **User-scoped integrations:** Gemini and SMTP credentials may be saved per user in an additive `user_integrations` table. AES-256-GCM ciphertext uses a versioned `v1` format with user/provider authenticated data, preventing a ciphertext row from being moved to another account/provider; `INTEGRATION_ENCRYPTION_KEY` must be exactly 32 random bytes encoded as 64 hex characters and is server-only. Endpoints return provider, connected state, and update time only; secret fields are write-only. A malformed key fails configuration validation; missing key prevents saving/decrypting but does not prevent server-environment fallback for users without saved credentials.
- **Credential key operations:** Generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Back up the key separately using protected secret storage and restore the same key alongside database backups. Losing or changing the key makes existing ciphertext unreadable; there is no rotation/re-encryption workflow yet, so rotation requires re-entering credentials or a separately planned migration procedure. Never commit or log the key/plaintext credentials.
- **Provider isolation:** Every integration lookup/write is scoped by authenticated user ID and provider. Gemini clients are created per request using the saved user key or configured server fallback and the configured model. SMTP transporters use per-user cache keys and are invalidated when credentials are saved or disconnected. Provider error details are replaced with generic messages. No live Gemini or SMTP calls have been verified.
- **Schedule contract:** Schedules accept an initial UTC instant and an optional recurring interval of 5–525,600 minutes. Calendar cron/timezone recurrence is deferred to avoid introducing a parser and timezone policy before a product requirement exists. A workflow must be `ACTIVE`; if it is deactivated, due schedules wait until reactivation.
- **Schedule durability and recovery:** PostgreSQL schedule rows are authoritative. The worker polls every 15 seconds, advances a due schedule with a compare-and-set on its previous `nextRunAt`, and creates the queued execution in the same DB transaction. It then enqueues by execution ID; existing startup recovery handles a crash after DB commit but before Redis insertion. If an enqueue fails, that occurrence is marked failed and is not retried. After downtime, a due occurrence runs once and the next interval starts from dispatch time (missed intervals are coalesced). Each future recurrence is an intentional new run, not retry of the previous run. A pause/delete race cannot cancel an execution already queued.
- **Scheduled trigger payload:** A schedule stores an optional generic JSON object used as each run's trigger input. Credential-like keys are rejected and the schedule API does not return the payload. This data remains in PostgreSQL for the schedule's lifetime; avoid secrets and unnecessary personal data and apply database backup/retention safeguards. No per-user schedule quota or inbound webhook trigger is implemented.
- **Background execution:** the approved worker phase uses Redis/BullMQ. A queued execution row in PostgreSQL is the source of truth; trigger JSON is persisted until a terminal status so the worker can recover missing queue jobs after restart, then cleared. API responses omit trigger JSON.
- **Queue recovery boundary:** each BullMQ job uses its execution ID, one attempt, and no stalled-job reprocessing (`maxStalledCount: 0`). A worker crash after an email/webhook may have succeeded is marked failed when BullMQ detects the stall; it is not replayed. This avoids automatic duplicate side effects but does not provide exactly-once delivery. Human inspection is required before a new execution.
- **Queue retention:** failed BullMQ jobs are retained so a still-queued DB record cannot be blindly re-enqueued under a fresh job after failure. Production Redis capacity and an explicit cleanup/retention policy are required.
- **Local infrastructure:** Compose starts only Redis with append-only persistence. The local database, API, client, and worker remain separately started. No live database migration or production deployment is part of this phase.
- **Sensitive execution data:** new step logs do not include trigger payloads, outputs, or provider errors. This intentionally limits persisted diagnosis while avoiding accidental credential/PII disclosure. No secret store, historical-log cleanup, or configurable retention exists; credentials in workflow configuration require a separate secure-storage design.
- **Validation tooling:** client ESLint and both TypeScript typechecks are available. `npm test` uses Node's built-in runner for focused server execution/configuration/queue-policy/analytics/account-settings/session-version and client tests. Server lint remains a placeholder.

## Decisions required before related feature work

1. **Additional trigger contract:** Manual and scheduled runs accept generic JSON objects. Decide whether and when to add inbound webhooks, which require signed secrets, replay protection, and rate limiting.
2. **Execution data policy:** Trigger JSON is now temporarily persisted while queued/running and cleared at terminal state. Decide production retention, backup protection, redaction of sensitive payloads, and operational handling of abandoned executions.
3. **Account scope:** Confirm whether workflows are per-user only or shared within teams/workspaces before adding roles or schema.
4. **Cookie security:** Verify the deployed client/API origin arrangement and required CSRF protections before changing cookie/auth behavior.

The queue and integration phases add additive Prisma migrations. Review and manually apply them only to the intended development database; no live/user database is modified by implementation.

## Repository reconciliation boundary

The separate Downloads checkout was read-only inspected and its four service diffs and two untracked patch artifacts remain untouched there. Selected safe behavior was independently implemented in this worktree: accurate step start timestamps, use of the latest AI output, preservation of execution errors when recording failure also fails, configured Gemini model/response checks, and SMTP transport cache invalidation after send failure. The race-prone duplicate guard, arbitrary delay cap/unit behavior, hardcoded model fallback, and webhook URL/response-body error disclosure were not carried over. Both checkouts share a base commit, but remain separate worktrees.
